### Entity relationships and access

```text
auth.users --1:1--> public.owners --1:N--> public.pets --1:N--> public.clinical_records
                               |                    |
                               +--> appointments <--+
                                          |
                              appointment_resources (one clinic calendar)
                                          |
                                  appointment_events (append-only)
auth.users --0:1--> staff_memberships (receptionist / veterinarian / administrator)

clinic_private.legacy_user_links: legacy numeric login -> Auth UUID, trusted importer only
```

- **Owner:** unique Auth user, no self-service ownership reassignment.
- **Patient:** pet belongs to one owner; client can only create/view/edit their own pets. Owner key cannot be updated via browser role.
- **Clinical record:** linked pet, procedure, measurements, author and timestamp; clients may read permitted pet history but cannot write; trusted veterinarian/administrator can append. No client role UPDATE or DELETE grants. Legacy text must be rendered escaped.
- **Appointment:** (pet, owner) is a composite FK, so even a privileged import cannot forge cross-owner pet linkage. Future start/end stored in `timestamptz`, displayed in a configured clinic time zone. One generic booking resource is created. `EXCLUDE USING gist` on resource plus half-open UTC range prevents overlaps among requested/confirmed/checked-in appointments **atomically**, including concurrent writers. Cancelled/completed/no-show reservations do not hold the slot. Validate local hours/holidays, appointment duration and acceptable transition state in application or a later trusted workflow.
- **Auditing:** append-only appointment status events are generated by an internal trigger, and no client INSERT/UPDATE/DELETE grant is given. Clinical immutability and staff author tracking are first-phase guarantees, not a complete clinical legal audit trail.
- **Staff access:** trusted server/SQL administrator grants an active membership. End users cannot self-promote, and user-editable JWT metadata is not trusted. Role checks query authoritative membership rows through a tightly scoped private helper function; revocation is effective on subsequent DB requests without waiting for JWT refresh.
- **Auth:** Supabase Auth, not imported Laravel password hashes. Public self-registration must create Auth identity and an owner row while properly handling failed inserts and verification; secure invitation/reset required for historical users. No frontend service-role/secret key or browser-exposed SQL admin endpoint.
- **Storage:** No patient files or storage buckets created yet; all future clinical attachments must use private buckets and owner/staff path policies, signed URLs and file limits before features are enabled. Do not put clinic PII in a public bucket.
- **Single clinic:** Multi-clinic tenancy is out of scope; one generic resource enforces one simultaneous booking at baseline. More chairs/vets/resources require explicit clinic operations approval.

### RLS and database permissions

- All 7 public application tables and the private ID mapping table have RLS enabled.
- `anon` receives **no table privileges**. Authenticated role receives only required SELECT and column-level INSERT/UPDATE grants.
- Clients may create owner profile (Auth UID from trusted request) and their pets; only own owner/pet updates. Client appointment inserts must use own pet, own owner, creator matching Auth UID, a real active resource and requested status.
- Client UPDATE is limited to **status** and RLS only allows cancelling their own requested/confirmed booking; no post-create updates to owner, pet, appointment times, concern or creator.
- Staff can see patient and appointment data, and vets/admins can add clinical records. Staff member insertion/role changes are **not accessible from frontend**.
- Clients see records only for their pets; clinical note UPDATE/DELETE is not granted.
- Internal `clinic_private.has_staff_role` is intentionally SECURITY DEFINER to check protected memberships without policy recursion; it is in an unexposed private schema, has an empty search_path, is granted only to authenticated and accepts only role names. No privileged function in public schema.
- The private `legacy_user_links` table deliberately has RLS without policies and no access to `anon` or `authenticated`. A Supabase security advisor **INFO** notice (RLS enabled, no policy) is expected for it; see [linter rule](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). Do not add a public policy merely to silence it.
- UPDATE policies combine USING and WITH CHECK. A later role-mutation endpoint, if needed, must remain server-only with an explicit owner-authorized audit trail.

### Free-only backup and recovery runbook

**Supabase Free does not include managed automatic backups or point-in-time recovery.** A reproducible schedule and an offline encrypted copy are mandatory for any pilot with real records.

- **Before every data migration:** take a source MySQL consistent export on an authorized terminal, for example `mysqldump --single-transaction --routines --triggers --default-character-set=utf8mb4 --hex-blob --no-tablespaces DATABASE > legacy-private.sql`. Use a protected authentication method such as a login path or interactive password; do **not** pass database password on the command line. Restrict file permissions and encrypt offline; never commit or attach it to a PR.
- **Before every Supabase schema change after real data exists:** export tenant data/metadata securely with a compatible `pg_dump` client, e.g. `pg_dump --format=custom --no-owner --no-acl --schema=public --schema=clinic_private --file=dawney-private.dump`, using authorized local connection configuration without exposing a URI/password in command history. This does not by itself capture Supabase-managed Auth users, role assignments outside app tables, Storage objects or platform configuration; back them up via a separately documented privacy-safe and provider-supported path.
- **Cadence for a real pilot:** at least daily encrypted app-data export and after any major operation, plus weekly offline copy. Test restore at least monthly and before a release, using a disposable/local PostgreSQL database **not** the live Supabase project. Document restoration counts, hashes, link consistency and RLS checks. Store two encrypted copies in separate owner-controlled locations (e.g. two physical storage drives) to avoid paid subscriptions. Secure passphrases in an independent password manager/secure vault.
- **Recovery:** stop new writes, identify last good checkpoint and data loss window, restore into *isolated* compatible database, run row/relationship/constraint checks, validate Auth account re-onboarding and private attachment access, then cut over only with owner approval. Never blindly `pg_restore --clean` into managed Supabase schemas or overwrite an active production database. If provider pause/loss happens, exports and recovery must work without live service availability.
- **RTO/RPO:** unknown until a measured restore drill. Never promise guaranteed service availability or automated restore under a free plan.
