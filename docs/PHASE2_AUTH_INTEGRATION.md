# Phase 2 — Supabase Auth integration, owner lifecycle and real-HTTP verification

**2026-11-13** · ChatGPT-owned scope · [PR #4](https://github.com/cmlagatuz/dawney-clinic/pull/4) · **Not a deployed application**

## What is implemented

- Dependency-free, ESM, React/TypeScript-ready Auth + PostgREST adapter: `packages/clinic-auth/src/client.mjs`, declaration file `src/client.d.mts`.
- Email/password signup with non-privileged profile-name metadata (only display defaults), resend confirmation email, verify six-digit OTP, password login, trusted `/auth/v1/user` lookup, refresh, logout and memory-only session.
- Owner-profile provision **only after a verified Auth session**: first read the authenticated user's own owner record, then insert `first_name`, `last_name`, optional contact info **without sending client-selected `user_id`**. Server sets user_id through `auth.uid()`, RLS, column grants and unique constraint. Concurrent duplicate insert retries by reading the existing owner record.
- Persisted owner profile survives logout/re-login because the data lives in Supabase PostgreSQL. The JS adapter itself deliberately stores tokens in memory only; full-page session persistence, PKCE redirect integration, and storage strategy are **future frontend work**, not currently promised.
- `supabase/migrations/20261113074938_phase2_verified_auth_and_staff_bootstrap.sql`: **additive third migration applied** to existing project, not a re-application of the original two. The private `is_permanent_user` helper checks the real `auth.users.email_confirmed_at`, anonymous flag, suspension/deletion status, and requires a valid Auth UID. The private `has_staff_role` helper now relies on it. Both are not public schema RPCs.
- `clinic_private.bootstrap_first_administrator(uuid)` and `clinic_private.grant_verified_staff(uuid,text,uuid)` are **SECURITY INVOKER** functions whose EXECUTE rights are revoked from `PUBLIC`, `anon`, and `authenticated`; they can be executed by a trusted project database operator, **never by a normal web account**. They check verified users, enforce one-time initial bootstrap, require an existing active administrator for later staff assignment, and preserve `assigned_by` for staff grants. No administrator has yet been bootstrapped.

## Required owner intervention for real sign-up, verification and HTTP testing

The project already exists. Do not create another project, upgrade a plan, disable email confirmations, or use real patient accounts.

1. Open [Supabase dashboard](https://supabase.com/dashboard/project/lgimhirgvresvbsdugac), go to **Authentication → Providers → Email** and ensure **Confirm email** is enabled. Under **Project Settings → API Keys**, copy the **publishable** default API key (starts with `sb_publishable_`). **Never use a secret/service-role key.**
2. Prepare two separate email addresses under your control that can receive the test verification emails. They must not be used by real patients or staff. Create different unique passwords of at least **8 characters with a letter and a number**, preferably 12+ characters and generated by a password manager. Do not share passwords, confirmation codes, email addresses or tokens in ChatGPT/Claude or commit them.
3. In [GitHub repository settings](https://github.com/cmlagatuz/dawney-clinic/settings/secrets/actions) go to **Secrets and variables → Actions → New repository secret** and create **exactly** these six names:

   | Secret name | Value you supply privately |
   | --- | --- |
   | `DAWNEY_SUPABASE_URL` | `https://lgimhirgvresvbsdugac.supabase.co` |
   | `DAWNEY_SUPABASE_PUBLISHABLE_KEY` | The enabled Supabase *publishable* API key from step 1 |
   | `DAWNEY_TEST_A_EMAIL` | Test mailbox A |
   | `DAWNEY_TEST_A_PASSWORD` | Unique password for A |
   | `DAWNEY_TEST_B_EMAIL` | Test mailbox B |
   | `DAWNEY_TEST_B_PASSWORD` | Different unique password for B |

4. On `master`, open **Actions → Clinic Auth contract → Run workflow**. Check **Supabase → Authentication → Users** first. If Account A is absent, select **`register-a`**; if Account B is absent, select **`register-b`**. **Do not register an account that already exists**, and never use both signup operations unnecessarily. The script submits one signup only and does not print credentials. Verify only the new account through its mailbox. If the link redirects to a nonworking site, check the email confirmation status in Supabase rather than pasting the link anywhere. If both accounts already exist and are confirmed, **skip registration completely**.
5. Run the same Actions workflow again with `test`. It logs in as both verified accounts, calls `/auth/v1/user`, writes at most two **synthetic owner profiles** (no pet, medical or appointment rows), makes authenticated PostgREST reads for both accounts, verifies one user cannot see the other's profile or create administrator membership, logs out and reauthenticates to prove the owner row persists. The job fails if RLS, credentials, email verification, or persistence fail. Review the GitHub Actions job conclusion; do not share raw logs containing any credentials (the script does not print them).
6. **Clean up test-only owner profiles/accounts** after testing in a trusted Supabase environment (and verify that no real records reference them). Since `owners.user_id` has a RESTRICT foreign key to Auth users, remove only the two specifically identified synthetic owner profiles first, then delete only those two Auth test accounts via **Authentication → Users**. Take a verified snapshot before any cleanup once real data exists. Do not run blanket `TRUNCATE`, `DELETE FROM owners`, or disable RLS. Confirm both test accounts are gone before clinical use.

If Supabase returns HTTP **429**, stop without retrying or resending. The hosted built-in sender is limited to approximately **2 emails per hour, per project**; requests also have per-account/IP limits. Check **Authentication → Rate Limits** and use the free quota after it replenishes. Do **not** disable email confirmations, re-register Account B to restore Account A, or purchase an SMTP plan. This test creates temporary nonclinical profile data only by explicit owner opt-in. Source: https://supabase.com/docs/guides/auth/rate-limits .

## First administrator and staff invitation (operator-only)

There is **no** built-in administrator account, default password, secret role or privilege escalation in signup. Authenticated clients cannot call these private DB functions. To bootstrap when the real clinic owner has finished verification:

1. Have the owner register and confirm their email through Supabase Auth using the future app or the Supabase dashboard. Verify `email_confirmed_at` on the correct Auth user. Do not copy their password into SQL.
2. In **Supabase → SQL Editor**, as the trusted project operator, locate the **UUID of the exact verified owner** (review email/ID in the dashboard). Invoke:
   ```sql
   select clinic_private.bootstrap_first_administrator('<VERIFIED_AUTH_USER_UUID>'::uuid);
   ```
   Replace the placeholder with the verified UUID; do not save personal addresses to repository files. The function locks the operation and fails if an administrator has already been created. Verify in **Table Editor → public.staff_memberships** that the UUID has `role = administrator` and `is_active = true`.
3. For each additional staff member, use **Authentication → Users → Invite user** and send the invitation using free quota. After the invite is accepted and the email is confirmed, inspect the corresponding UUID; have the active administrator explicitly approve the role and record the authorizing administrator's UUID. Then, **only in SQL Editor**:
   ```sql
   select clinic_private.grant_verified_staff(
     '<VERIFIED_INVITED_AUTH_USER_UUID>'::uuid,
     'veterinarian',
     '<AUTHORIZING_ADMIN_UUID>'::uuid
   );
   ```
   Valid roles are `receptionist`, `veterinarian`, or `administrator`. Confirm the exact `staff_memberships` record and `assigned_by` value. Never offer these database functions in a browser RPC or grant them to `authenticated`.

The manual SQL workflow is a **restricted initial bootstrap**, not a finished staff-management UI. Before scaling, build a reviewed server-side invitation/revocation service with its own role-change audit and request validation. The current schema's roles are single-clinic. Do not grant service-role access to the frontend.

## Future React integration

Use the ESM package from `packages/clinic-auth` (with `client.d.mts` TypeScript declarations), for example:

```ts
import { createClinicAuth } from '@dawney/clinic-auth'
const clinicAuth = createClinicAuth({
  url: import.meta.env.VITE_SUPABASE_URL,
  publishableKey: import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY,
})
const result = await clinicAuth.signUp({
  email, password, firstName, lastName,
})
// If verification_required, show "Check your email".
// After verification, signIn then ensureOwnerProfile; display actual persisted data.
```

`VITE_SUPABASE_PUBLISHABLE_KEY` is a public client key, **not** an admin/service-role key. Do not ship a secret key. Install the module via a future workspace/alias or relative ESM import; there is not yet a modern React app or root workspace. UI should provide verification/resend, error, loading, keyboard and accessible states, and route handling for email links. Use RLS as the security boundary, not frontend conditions.

**Caveat:** This Phase 2 adapter deliberately avoids refresh-token persistence to prevent an unreviewed storage decision; pages will require re-login on full reload. For the production React app, strongly consider integrating the official `@supabase/supabase-js` with pinned package lock and appropriate client-side session/PKCE handling. Never store the service-role key or log access/refresh tokens.
