## Authorization and data boundaries

- `staff_branch_memberships(user_id,branch_id)` requires explicit **trusted operator** grants and has no API write privileges. The legacy `staff_memberships` role and active flag must ALSO match the branch role: an inactive/revoked/global-role-mismatched account is denied immediately. Administrators only cross branches if each one is explicitly assigned. No automatic staff backfill or elevated default admin. A user may have multiple explicitly authorized branches.
- `public.assert_staff_branch(branch_id)` checks the fresh SQL/Auth membership and raises `42501` on unauthorized switch. It does not store a trusted active branch. UI-selected `active_branch_id`, JWT user metadata, URL query strings and client filters never grant authorization. RLS always independently recomputes the branch scope from the current Auth UID and DB grants. Signing/identity verification is delegated to Supabase Auth; raw client JWT strings are not authorization data in SQL.
- Owner and pet IDs are **shared organization-wide**, but normal staff can only SELECT shared owner/pet identity when a patient has an appointment at one of **their explicitly granted** branches. Medical records, appointment events and appointment status changes are branch restricted; a Naga vet cannot view a Cavite chart of the same pet. A verified true owner may see their own longitudinal record across branches. The strict staff clinical read is limited to veterinarian/administrator with an actual visit at the record's branch, not just global staff status. Receptionists cannot browse the chart.
- `appointments`, `appointment_resources`, `clinic_services`, `clinical_records`, and `pet_attachments` gain nullable, constrained `branch_id` fields. Existing rows have NULL **unknown**, not forced Naga. New appointment branch is **derived on the server from a branch-attributed resource**, never accepted merely from a browser. Mismatched service/resource branch raises `23514`; branch change after insertion is forbidden except trusted NULL→known attribution with a pre-existing evidence row. Existing `requested` and `confirmed` transitions, owner cancellation rules, nonce index, GiST resource conflict rule and taxonomic Chow Chow mapping remain unchanged.
- Protected legacy global permissive policies are not dropped: additional **AS RESTRICTIVE** RLS is AND-ed onto old owner/pet/appointment/clinical/attachment/Storage policies. A prior global staff membership is never sufficient by itself. Original unaffiliated historical appointment/patient rows remain visible to their authenticated true owner, but not to generic staff until provenance is reviewed.
- The original legacy global `clinic_booking_policy` is denied by a restrictive read policy. The old `request_service_appointment` and legacy direct inserts therefore **fail closed** until a separately reviewed branch-aware booking RPC and approved branch-specific hours/resources/services are provided. This is an intentional **functional compatibility blocker** of applying this early migration: **NO ROLLOUT GO** until the frontend/new RPC and Naga policies are owner-approved. A valid future migration may preserve the original RPC signature by enforcing/deriving branch from selected resource; never silently auto-map historical records or relax the appointment status lifecycle.
- Existing pet-based Storage object names have no branch. Their old permissive policies are intersected with new restrictive predicates: owner-path read/insert only for the verified actual owner; staff SELECT requires a branch-attributed `pet_attachments` row plus approved branch visit and authorized vet/admin; staff clinic-path uploads are **intentionally denied** until a separately reviewed branch-encoded object key + pre-authorized upload/cleanup flow exists. Do not weaken the original bucket/privacy policy. This proposal creates no buckets, files or objects.
- `branch_encounters` ties appointment, branch and pet through a composite FK. Treatments must reference matching encounter/branch. Both tables are RLS enabled; there is **no direct client INSERT** until reviewed encounter/treatment commands and clinical-consent rules. `branch_inventory_movements` is an isolated no-client-grants shell for later Issue #78, not inventory activation. **Referrals / cross-branch clinical data sharing are not granted in this candidate**: require separate recorded consent, referral authorization, patient-context and immutable audit evidence first.
